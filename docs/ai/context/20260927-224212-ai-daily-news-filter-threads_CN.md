## 验证

测试期 `AI日报/_测试_左边缘黑点_20260927/` = `_旧稿/_试跑_宽屏_20260927`（9月27日试跑，5 条，20:30 用旧脚本渲染）的副本。它必须放在系列根下：引擎按 `../../../素材/` 找素材，在 `_旧稿` 里渲染不了。脚本和结果都在它的 `验证/` 里。

检测方法（`验证/edgecheck.py`）：把每一帧按原样解码（不转像素格式，单线程滤镜），对左边缘 x0..4、x5..8、x0..8 三组列，算每一行比上下两行暗多少，再减去同一行在对照列 x16..23 的同样数值（横跨整行的画面内容会抵消）。第 72、144、…、1008 行是黑点行，其他行（去掉黑点行的上下邻行）当基线。比较黑点行暗 ≥1 级的比例和基线，再看按行号除以 72 的余数哪一组最暗（周期性）。

1. **旧成片确实有黑点**：`_旧稿/_试跑_宽屏_20260927/制作/build/main.mp4`，每 5 帧取 1 帧（848 帧）：x0..4 黑点行暗 ≥1 级的比例是 43.4%，基线 1.45%；770 帧有 ≥3 行，最深 18.8 级。深色底上很淡（例如 23 → 20）。上传版（H.265 约 150 kbps）大部分被压平了（2.5%，基线 0.66%）。旧的补边片头片尾没有黑点。
2. **同一批帧，新旧命令**（`convert_compare.py` → `convert_compare_result.txt`）：Chromium 截的 JPEG q95（和脚本送进 ffmpeg 的字节一样）从 stdin 送给 22:13 前和现在的 ffmpeg 命令。每个版本出两份原始帧（就是 x264 收到的画面，用 `-qp 0` 无损编码解回来逐字节核对过），另出一份实际编码参数的 .mp4。
   - 2340，日报引擎 24 个时刻：旧命令两次输出不一样（多线程竞态）；黑点正好在第 72、144、…、1008 行的 x0..5，亮度最多暗 18 级，色度在 x0..2 也偏色。新命令两次输出一样、没有黑点。新旧只差这些像素：x0..8 以外 0 个亮度像素不同。
   - 2340，纸白页面：旧命令的黑点是纯黑（Y 0，底色 233），很明显。
   - 1920（同一引擎开 1920 窗口、纸白页面）：新旧命令送给 x264 的帧逐字节相同，编码出的 .mp4 也逐字节相同。
3. **PNG 管线**（片头片尾走的《原LAI如此》`render.py -o`，`pngpipe_compare.py`）：1920 和 2340（canvas）加不加这个参数都逐字节相同，都没有黑点。1920 的输出 md5 和日报会话 22:17 渲染的 `_试跑_API/制作/build/intro_raw.mp4` 一样。20:27 和 22:17 两次渲染的片头有细微差别，只在中间的动画图形上（每帧几百个像素），和这个参数无关（上面已证明逐字节相同）。
4. **脚本本身**（`验证/script/`）：重建的旧 `render_parallel_wide.py` 和技能里现在的版本，同一个引擎和时间轴，正片前 6 秒（180 帧，3 路）：
   - 旧：180 帧全有黑点（黑点行 81.2% 暗 ≥1 级，基线 1.42%，最深 15.3 级）。
   - 新：0 帧有黑点。唯一被标出来的黑点行是第 576 行，那是画面内容：无损截图里那里本来就有一个亮块的下边（x0..4 是 54，x16..23 是 45）。
   - 新脚本跑两次，解码后逐像素相同。
   - 新旧两份在别处也有细小差别，那是 x264 的输入变了之后正常的编码差异：和正确的源画面比，新旧误差一样（x16 以外平均 0.399 / 0.400 级，PSNR 46.0 / 45.9 dB），黑点位置的误差从 2.24 降到 0.06。
5. **实际运行**：日报会话 22:15–22:19 用新脚本渲染的 `_试跑_API` 正片、成片都没有黑点（848 帧里 0 帧，改前的试跑是 770 帧）。
6. **1920 这条路**：日报的正片只出 2340（`render_wide.W` 写死），没有 1920 正片。上面第 2、3 条说明这个参数对 1920 的 JPEG 管线和 PNG 管线都不改变输出（逐字节相同）。

## 顺带发现（没改）

- `render_parallel_wide.py`（和《原LAI如此》的 `render_parallel.py`）出的 main.mp4 是全范围（ffprobe 显示 `yuvj420p` / `color_range=pc`），片头片尾是 tv 范围；`-c copy` 拼接后整个文件标 tv，但每段自己的 SPS 还在。ffmpeg 解码成片的正片部分颜色是对的（和 Chromium 画面比，暗部偏差 < 2 级），上传版（H.265）也正确转成了 tv 范围。只认第一个 SPS 或容器标记的播放器，可能把成片（不是上传版）正片部分的暗部显示得更暗。B 站拿到的是上传版，不受影响。要统一，可以在 render_parallel 编码前把范围转成 tv；这会改变每一帧，要单独测试并经用户同意。

## 工具

- `验证/edgecheck.py <视频> [--every N] [--t0 秒 --t1 秒]`：有黑点退出码 1。判定：黑点行暗 ≥1 级的比例 ≥ 2%、超过基线 5 倍，而且平均多暗 0.1 级以上。片头这种满屏颗粒的画面基线很高，看“黑点行是否明显高于基线”，不看绝对数。
- `验证/video_diff.py a.mp4 b.mp4`：两段视频逐帧比较，分 x0..15 和其余部分统计。逐帧流式读（第一版把两段全读进内存，整段正片要约 40 GB，已改）。
